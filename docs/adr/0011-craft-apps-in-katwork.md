# 0011. Craft apps in KatWork: Kats drive them behind a policy proxy, people watch and take over through one bridge

- Status: Proposed (2026-10-24), with the sub-project 2a plan's Craft round (founder decisions R23–R28, R33, R34 and R36, and R35, decided by the coordinator under the founder's delegation of 2026-10-25); it becomes Accepted when the founder approves that round
- Decision owner: Founder
- Spec: §1.2, §2, §5.2, §9, §9.1, §10, §13, §17, §18, §19 items 2 and 7; amends §1.2's "live Kat control" non-goal and §9.1, and extends `docs/adr/0007-evidence-model-and-source-refs.md` (claims carried across versions, the `not_checked` outcome)

## Context

The storytold Craft suite is 13 desktop-class office and creative apps written in Rust: WordCraft (documents), GridCraft (spreadsheets), PdfCraft (PDF), DeckCraft (slides), DesignCraft (page layout), VectorCraft (vector art), FigCraft (interface design), PhotoCraft (layered images), LightCraft (photo development), CADCraft (2D CAD), FilmCraft (video), EffectCraft (motion graphics) and SoundCraft (audio). The founder decided (R23–R28) that all 13 are in sub-project 2a: Kats drive them, people watch the work live in the office and can take over, and they are built before the meeting-minutes demo, which shows them.

What the apps' own repositories show, at the commits the forks start from:

- **Every app has a headless MCP server**, `<app>-cli mcp`, newline-delimited JSON-RPC 2.0 over stdio (protocol 2025-06-18), with a headless in-process engine on the CPU. Most also offer a mode that attaches to a running desktop app (`--connect`, `--bridge`, `--attach`; VectorCraft attaches to `127.0.0.1:7979` *by default* unless `--headless` is passed), and the desktop apps run loopback control servers, several with no authentication.
- **None of the servers has a per-command allowlist.** Each exposes a generic command tool (`execute`, `execute_command`, `run_command`, `command_run`, with batch forms) that reaches the app's whole command registry: hundreds of commands, among them LISP with file writes (CADCraft), document JavaScript (PdfCraft), After Effects-style scripts and a preference that opens their file and network access (EffectCraft), plug-in installs (VectorCraft, PhotoCraft, FigCraft, EffectCraft), a public sharing server (FigCraft), model downloads (LightCraft, EffectCraft) and native CLAP, VST3 and AU plug-in hosts that load code in-process (SoundCraft). The tools' read-only annotations are absent (CADCraft, SoundCraft) or wrong (FigCraft's `export` writes a file). Nine apps take `--automation-read-root` and `--automation-write-root`, and seven of them print a line saying their files are confined (PhotoCraft and EffectCraft print none); GridCraft, CADCraft, LightCraft and FilmCraft have no such roots, and every app documents a check-then-open race.
- **Only four web builds have a host bridge**: GridCraft, PdfCraft and CADCraft speak `postMessage` to a same-origin parent (`?host=parent`), and VectorCraft installs a JavaScript object, `window.vectorcraft`. The other nine have none; FigCraft's web build cannot open a file at all except by joining a live session. No web build has a read-only mode.
- **Thai wraps between words in only two apps.** VectorCraft uses ICU4X's line segmenter (dictionaries on the desktop, LSTM models on the web), and PhotoCraft has dictionary breaking on the desktop only. The others break Thai at spaces only, or not at all; CADCraft does not shape Thai marks, LightCraft draws its rendered text glyph by glyph with no Thai face, and most web builds carry no Thai font.
- **Licences.** All 13 are MIT OR Apache-2.0. The ArtCraft name, wordmark and logos are trademarks that a distributed modified version must remove. Several apps implement patent-pool video and audio codecs in software with no patent statement, and some ship or download model weights under restrictive licences.

## Decision

**Runtime.** The apps run only in the `katwork-craft` sidecar, a container on an internal network with no egress that is not a child process of the server. Each Kat session starts one MCP process, launched from that app's policy file, as its own throwaway user (founder decision R22, applied per session): a fresh uid and gid from a range that does not wrap, inputs it can read and not change (LightCraft's opened photo excepted: it sits in the session's output folder so the app can write its XMP sidecar beside it, and a save whose photo bytes changed is refused), writes only to its own output, home and temporary folders under a disk cap, inherits no descriptor but stdin, stdout and stderr, runs in its own process session, no capabilities, a seccomp filter that refuses every socket, `AF_UNIX` included, io_uring, and all shared memory and message queues, resource limits, and every process of that uid killed when the session ends, double-forked ones included. `AF_UNIX` is refused because abstract Unix sockets share one namespace across the container, whatever the uid, so two sessions could otherwise meet through one; the apps' MCP servers open no socket (their Unix-socket code serves the desktop apps: D-Bus theme and portal dialogs, single-instance locks, CUPS printing). No tenant data goes on a command line, because every process in the container can read every other's: the Kat's author name reaches WordCraft over the MCP pipe (`file.setAuthor` in the session's open recipe), never as `--author`. No desktop app, control port, attach flag or GPU mode exists in the image; VectorCraft always runs `--headless`.

**The policy proxy is the boundary, not the app.** Between KatWork and each MCP process, the sidecar decides every call from a per-app policy file, codex execpolicy style: each tool, each command id of the command and batch tools, and each argument constraint is `allow` or `forbidden`, with a justification and examples that must decide as stated when the policy loads. Unknown tools and commands are forbidden; one forbidden batch step forbids the batch; every declared path must be a logical path inside the session's `in/` or `out/`; arguments are closed-world, so a property no rule names is refused, and so is a path-like value under any key the policy did not declare as a path, whatever the key's case or suffix; the proxy rewrites paths both ways, so no model sees a uid or a session folder; a request from an app's server to the client (sampling, elicitation, roots) is refused. The app's own roots, where it has them, are a second lock. MCP annotations decide nothing.

**Hidden text stays out of the model here too** (founder decision R33; `docs/adr/0010-untrusted-content-posture.md`). Every rule and command rule states whether its reply can carry document text (`returns_text`). When the file a Kat opens, or one of its inputs, holds hidden text by KatWork's own readers, cannot be read by them (among the formats they read), holds parts they skip with a warning (embedded objects, macros, a PDF's scripts or attachments: founder decision R34), or was saved by a hidden-content session, the session is a hidden-content session for its whole life: the proxy refuses every `returns_text` rule (`craft_hidden_content`) before the app sees the call, the step is logged as refused, and the Kat reads the file with `read_file`, which leaves hidden text out. The apps' error messages are withheld in such a session, since several quote the document. Editing, saving and previews still work, but for a few editing tools whose replies echo document text (GridCraft's `set_cell` replies with the computed value). Because the Kat's own edits can make hidden text visible (a white cell recoloured, a formula pointing into a hidden sheet), such a session's tool results carry no document text at all: GridCraft's grid facts give a cell count only, a save's receipt names uncited figures by location only, the session cannot save CSV, text or Markdown, and every version it saves is marked `hidden_derived`, so later Craft sessions on it are hidden-content sessions too and `read_file` refuses it, naming the file it was made from, and `check_artifact` returns no text for it (decided by the coordinator under the founder's delegation of 2026-10-25, not a founder quote). A person's session in the app runs the same check on the file it edits, so what a person saves from such a file is marked too. In a normal session KatWork, not the app, builds GridCraft's grid preview, from the cells its own reader finds visible in a snapshot of the session's workbook. A canary check in the image's self-test calls every allowed rule, mutating ones included, each in a fresh session, on a document whose every text holds a canary string, so a rule that returns text unmarked fails the build; it reaches only the six apps whose files KatWork reads, and it misses text a reply carries only in a state its first example does not produce. Formats KatWork cannot read, and parts its readers skip without a warning, get no hidden-text check; ADR-0010 names those residual risks.

**One action log, with no unlogged mode.** Every step of a session, the Kat's calls, the harness's previews and saves and a person's lease changes, saves and edit counts, is one append-only, hash-chained entry in one format: actor, tool and command, decision, the document revision before and after, the version a save made and a preview's hash. Entries hold ids, hashes and summaries that code builds from the arguments' shape; they never hold document text or a file name, so a deletion never has to redact them. A session is reachable only through KatWork's Craft tools, and the sidecar refuses a call KatWork did not number; a call whose log entry a cancellation lost leaves the numbers out of step, so the session takes no further call, and a take-over saves nothing from such a session.

**The control lease: one active editor at a time.** Each file has one lease in KatWork, held by nobody, a Kat session or a person, with a fencing token that grows on every change. A Kat's session holds the lease of the file it is editing (a session opened from a template holds the lease of the file its first save in the app's own format creates; an export to another format moves no lease); another Kat gets `craft_file_busy`, and so does a writer tool naming the file. A person who takes over holds the lease at once: KatWork freezes the Kat's session, so no later call of it reaches the app, lets its call in flight finish, saves the Kat's unsaved work as a version, and only then lets the person edit; every Kat call on the file, and every writer tool naming it, is refused with `human_has_control` before the app sees it, a Kat call that fails afterwards never touches the person's lease, and the Kat's run stops at its next tool boundary as `needs_input` (the person is the input it waits for). The person's save is a new version, accepted only with the current fence and the version it started from; a save of an input, or of a file not in the app's own format, becomes one new file, `<stem> (edited)`, which their later saves version. Hand-back posts the person's own message with a short hand-off note, and SP1's follow-up path continues the Kat from the new version; an idle lease (10 minutes) or a long one (60 minutes) ends with a notice and never a message on the person's behalf. Any member may watch; taking over is open to members unless a Space admin limits it to admins.

**One bridge, protocol v1.** Every app's web build speaks the same protocol, from one shared crate (`katwork-bridge`, MIT OR Apache-2.0, in its own repository, pinned by commit): `kw:load {name, bytes, readOnly}`, `kw:setReadOnly`, `kw:state {dirty, revision}`, `kw:save` answered by `kw:saved {bytes}`, `kw:leaseChanged {holder}`, and `kw:ready` and `kw:failed`. The nine apps without a bridge are forked under the founder's account and get the crate; the four with one get an adapter to it inside their fork; upstream PRs are opened for both. In KatWork mode an app starts empty, keeps nothing in browser storage, hides its pickers, downloads and printing, enforces read-only at its engine's command entry and every path that edits outside it, wakes on each bridge message, and shows its banners in the person's language.

**The web builds live on their own origin.** They are served by `katwork-craft web` from a separate origin (`KATWORK_CRAFT_WEB_ORIGIN`), on a different host and a different site from KatWork's, checked at startup: a sibling subdomain is the same site, whose script could set cookies KatWork receives, so it is refused unless an operator overrides it. A small host page on that origin frames the app same-origin, as the existing bridges require, and relays protocol v1 to the KatWork window with exact origin, source, token and type checks, under a strict policy (`script-src 'self' 'wasm-unsafe-eval'`, inline scripts moved out at build time, `frame-ancestors` the KatWork origin). The web server is not on the sidecar's network, and it refuses service-worker scripts; the host page unregisters any service worker before it frames an app. A document reaches the app only through the relay, from KatWork's window. The per-opening token stops a stale tab from speaking for a current one; it does not stop a compromised app, which shares the host page's origin. What protects KatWork is the origin and KatWork's own checks on every relayed save: its type, size, lease fence and base version.

**Evidence for Craft outputs.** A Craft save goes through the writers' commit path: read back with KatWork's own readers, checked by GridCraft when it is a workbook, committed under the artifact lock contract with its receipt. KatWork gains a PPTX reader with the package guard and fuzz target of the DOCX reader; in sub-project 2a it hides only text on a hidden slide, in a hidden shape or group, or off the slide, and all other PPTX text is suspect, never full quality, so a claim citing a deck stays unverified (founder decision R36: all PPTX text is suspect in sub-project 2a); sub-project 7 owns precise PPTX visibility. Claims survive an edit by being found again in the new version: by their marker (a DOCX bookmark, an XLSX cell note), else by their exact text found exactly once in visible text, else they are `unverified` with `claim_lost_in_edit`. A Kat may add claims at save time, each of whose texts must be in the saved file once; a person adds none. A figure inside a carried claim is not listed as uncited. Quantities a save adds outside a claim are listed as uncited, as for the writers. Outputs KatWork cannot read (images, vector art, CAD, video, audio, the apps' own formats) are labelled "not checked against sources". Inputs are cited only from what KatWork reads: DOCX, XLSX, PDF, text, PPTX and OCR's text; citing CAD drawings, audio, video or image content is deferred.

**Thai.** Every app that lacks it wraps Thai, Lao, Khmer and Myanmar between words with ICU4X's line segmenter (dictionaries on native builds, LSTM models on the web, VectorCraft's approach), embeds KatWork's bundled Thai fonts (Sarabun and Noto Sans Thai) as its first Thai fallback, and has a Thai gate test that fails, never skips, without a Thai face; CADCraft also shapes Thai with HarfRust and LightCraft shapes its rendered text. The image build runs each app's gate.

**Provenance.** The image is built by KatWork's CI from the pinned fork commits, published under the founder's GitHub container registry, and pulled by digest; the build's per-file SHA-256 list is signed with Sigstore keyless signing in GitHub Actions, and the sidecar re-hashes every listed file and verifies the signature offline at startup. A local build, from an override Compose file, is unsigned and runs only when the operator opts in.

## Alternatives considered

- **The UI plane: run each app windowed on a virtual display and stream it** (VNC or WebRTC), with the person's input forwarded only for the lease holder. Rejected for SP2a: the apps' web builds run in the person's own browser at full fidelity, the MCP servers give the Kat typed commands, and a streamed desktop per session would add a display server, GPU or CPU rendering and a stream to every session. It stays an SP7 option for what the MCP servers cannot do.
- **The web app dials out to a broker (reverse connect)**, so the person's tab is the live engine the Kat drives. Rejected: it needs a protocol the Craft maintainers would have to accept upstream before KatWork could rely on it, and it would put the Kat's session in a person's browser.
- **Co-editing through a CRDT.** Rejected: the apps keep their own document models and undo; a CRDT would be a second source of truth, and one editor under a lease avoids lost edits by construction.
- **Trusting the apps' roots and annotations, with no proxy.** Rejected: four apps have no roots, annotations are missing or wrong, and every command tool reaches the whole registry.
- **Filtering hidden text out of each app reply**, instead of refusing the tools that return text in a hidden-content session. Rejected: KatWork would have to parse 13 apps' reply shapes and match their text to its readers' hidden blocks, and one missed shape would leak; refusing by rule needs only the policy, and `read_file` already gives the visible text.
- **One-shot CLI calls per step, with no sessions.** Rejected: most apps keep their document in the session's memory, and a reload per step loses undo, selection and unsaved state.
- **Building the apps from upstream, unmodified.** Rejected: plug-in hosts, script engines, network clients and patent-pool codecs would ship, nine web builds could not be embedded, Thai would not wrap, and the brand terms do not cover a modified build.

## Consequences

- KatWork maintains 13 forks and one bridge crate, and follows their upstream PRs; a fork moves back to its upstream once its changes land there.
- The first local image build compiles 13 applications and their web builds and takes a long time; operators pull the CI-built image by digest instead.
- A person editing a Kat's file and a Kat editing it never happen at once: the Kat waits, and the hand-off note tells it what changed.
- A claim a person changes is lost, not re-checked: a figure KatWork never cited is listed as uncited rather than passed.
- One origin serves every app and opening in sub-project 2a, so script that runs on it once can leave data in its storage or reach another of its tabs (`BroadcastChannel`, WebRTC); the apps keep nothing in browser storage in KatWork mode and a CI job checks that, but only per-session origins (sub-project 7) end this.
- The office monitors, a streamed UI plane, citing CAD, audio, video and image content, DWG, long renders as background jobs, per-role tool tiers, per-session origins and one container per workspace are later work (SP6 and SP7).
